# #396 Review fixes (#367): stream agent output and take polling off the turn path (LT-5, LT-13, LT-15, LT-16) [review/waiting]

All four findings in my batch are fixed, and the PR is open into #367's branch. Agent text now appears about 30 ms after the provider starts writing, instead of only once the whole message is done. On the tree merged with the parent's latest `99bdd78c`, typecheck is clean and every test file I touched passes, including the full `pipeline` (60), `gateway` (63), `workflows` (29) and `web-regressions` (109) suites.

## Status by finding

**LT-5 fixed** — commits `60fc1224`, `00003a84`, `b8269bd1`, `5e919444`.
- **Throttle:** in `src/agent/runtime.ts`. The first chunk is published at once, then at most one update every 150 ms, each carrying the latest text. Pending text is published just before the completed message and at a successful turn end. A failed or cancelled turn publishes nothing more.
- **Claude Agent SDK:** now asks for partial messages and streams the main agent's text; sub-agent streams stay out of the main bubble.
- **Codex app-server:** streams `item/agentMessage/delta` instead of waiting for `item/completed`.
- **ACP:** it did emit deltas, but the console treats each emit as the whole message, so it only ever showed the last chunk. It now sends the growing text.
- **Messages API and Responses API:** now request streaming and rebuild exactly the object the non-streaming call returns, so usage, tool calls, stop reasons and error classification are unchanged. The tests compare the streamed and non-streamed turns and they come out equal.
  - A mid-stream error event is reported with the same HTTP status the error would have had before the stream started.
  - A connection cut mid-stream is treated as a retryable interruption, never a finished turn.
  - Responses that aren't event streams (proxies, stubs) are still read as plain JSON.
- **Final message recorded once:** the completing item records it; an adapter no longer re-sends text it just streamed.
- **Console:** the live bubble used to disappear after an agent's first reply, so nothing streamed after that. It now:
  - streams the whole turn;
  - is replaced by the completed message, so the text shows once;
  - clears on a new or failed attempt and on cancel;
  - ignores tool lines;
  - stays in the streaming agent's own conversation (a reviewer's text no longer lands in the Do pane).
- **Tests:** `tests/agent-streaming.test.ts`, `tests/codex-app-server.test.ts`, `tests/acp-agent.test.ts`, `web/stream-refresh.test.cjs`, and a new browser test `web/live-stream.browser.test.cjs`. The browser test drives the full console: updates patch the bubble in place with no repaint of other rows and no API reads, taking about 4 ms from socket to screen.

**LT-13 fixed** — `fac28b94`, test in `tests/followup-injection.test.ts`.
- The workflow is now queried only when a follow-up has been recorded for the task (the API already records each one as a `conversation.message` event) or the workflow has republished its view. The first check in a turn always asks.
- A recorded follow-up keeps being asked for up to 10 s until it comes back, and a query every 30 s covers anything sent without a record.
- Polling still happens every 1.2 s, so delivery latency is unchanged. The real-Temporal test still delivers a follow-up inside the running turn.
- The runtime's duplicate 1 s heartbeat is gone; the activity's own keep-alive remains.

**LT-15 fixed** — `15eb3229`, tests in `tests/worker-process.test.ts` and `tests/gateway-event-authorization.test.ts`.
- **Relay wake-up:** in process-worker mode, the worker process now notifies the main process after each event it writes, and the relay wakes immediately. The 500 ms poll stays as the fallback.
- **Authorization cache:** each open socket decides a task's visibility once and reuses it until its token expires, capped at 60 s. A failed lookup is retried rather than cached.

**LT-16 fixed** — `ae6cb147`, tests in `tests/task-start-critical-path.test.ts`.
- The advisory GitHub merge check now runs alongside the workflow start instead of before it. The created task still carries the warning and it is still logged. The check that can reject a task still runs first.
- Once the gateway has set up a project's wiki (startup does this for every project), task create and queue refresh it in the background instead of waiting.

## Before and after
From `benchmarks/first-text.ts` (added in `87eb8578`), run on both the base and this branch. It uses a local fake provider writing 120 words at 40 per second; no network or credit.

| | Before | After |
|---|---|---|
| First visible text, Messages API | 3009 ms | 36 ms |
| First visible text, Responses API | 3009 ms | 29 ms |
| Live-output events per 3 s message | 1 | 22 (unthrottled would be 120) |
| Task create → workflow start (GitHub check 250 ms per call) | 513 ms | 5 ms |

From the tests:
- **Workflow queries (LT-13):** 20 quiet polls cost 1 query instead of 20. That is roughly 1–3 queries a minute per running turn instead of about 50.
- **Authorization lookups (LT-15):** 25 events for one task cost 1 lookup instead of 25.
- **Relay delay (LT-15):** estimated, not measured — up to 500 ms before (the poll interval), about one message hop now.

## Trade-offs
- Streaming writes more live-output rows: about 7 per second per streaming agent, still deleted when the task finishes. I kept "each event carries the whole text so far" rather than deltas, because any single event is enough to redraw correctly.
- I capped the socket authorization cache at 60 s instead of the socket's whole lifetime, so a revoked token or removed member stops receiving events within a minute. You asked for "lifetime with re-check on expiry"; the cap is my change.
- A follow-up sent as a raw Temporal signal, with no record in the event log, now arrives within 30 s rather than 1.2 s. Every production path goes through the API and is recorded. Two end-to-end tests that signal Temporal directly now also write that record.
- The task-create response still waits for the GitHub check so it can include the warning. Only the workflow start stopped waiting.
- The Activity feed no longer shows streamed text chunks. The server still sends them in its initial 300-event page, so that page can show fewer rows.
- I left the adapters' own 10 s heartbeat timers in place. They were never among the two 1 s timers the finding names.
