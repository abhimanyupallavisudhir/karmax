# Comprehensive code review — 2026-09-08

Scope: the whole `karmax` repository (≈154k lines: `src/`, `web/`, `tests/`, docs), the `panagent`
Python repository, and the project wiki. Method: a lead reviewer plus area reviewers reading every
module (gateway, platform API/authz, store, autonomy/vault, workflows/coordinators, activities and
agent adapters, world providers and git, integrations, web console, packages/wiki/billing/misc,
panagent), each finding verified against the actual call path before being kept. Findings that
could not be confirmed were dropped.

The first section lists what this change **fixes**. The second lists what remains **open**, ranked,
with a suggested fix each — it is meant to be turned into tasks. The third covers code quality.

Severity: CRIT = exploitable by an ordinary agent/user across a trust boundary or destroys data;
HIGH = same but needs a privileged-but-untrusted actor (an organization admin on a hosted cell, a
compromised sandbox) or is a clear correctness bug on a main path; MED = real but bounded; LOW =
hygiene.

## 1c. Runtime smoke test (mock agent, fresh home)

The console was booted (`KARMAX_AGENT_PROVIDER=mock`, empty `KARMAX_HOME`) and driven in a browser:
first-run setup, project list, quick-add task, task page live updates, Review confirm, organization
and project settings. Everything that was exercised worked without a reload; no console errors, no
failed requests except the ones below. What it surfaced (all open, none fixed here):

* **Email-verification nag on an installation with no outbound email.** After setup the banner
  "Confirm your email … Resend link" is shown; "Resend link" reports "Confirmation email sent — check
  your inbox" (`/api/auth/send-verification-email` → `{status:true}`) although no SMTP is configured
  and nothing can arrive. The banner should not appear, and the resend should fail honestly, when the
  installation has no email service. The success toast also appears **twice**.
* **Every workflow parameter is a list filter/group/sort.** The task list's Filter, Group and Sort menus
  list every manifest field of every workflow, including installation-level settings that are not task
  attributes ("Concurrent agent turns", "Branch to merge" from merge-only, "Pull-request landing
  authority", the three "Review route" and "Responder" fields…): ~30 filter entries and ~55 sort
  entries for a fresh project. Only fields with `scopes` including `task` (and a `searchable` flag)
  should be offered.
* **Redundant fetch storms.** Creating one task issued the same `/search?q=…` request four times in a
  row (one per WebSocket event; the debounce is per event type, not per burst). Organization settings
  issues 53 API requests to render, fetching `/api/defaults/global/software-dev` four times and
  members/teams/users/inbox twice each; project settings issues 48 with the defaults fetched four
  times. These are what makes settings pages feel slow.
* **First run lands on the profile page**, not the project; a new default project has no seeded
  preparation task although SPEC §4.6 describes one for new projects (the seeding only runs for projects
  created through the API).
* **The stage chip of a task waiting at Review says "Waiting for input"**, the same label as a task
  paused for a human question; the Move menu offers "→ Back to Working / → Draft / → Done" but never
  names Review. The Confirm/Cancel footer is the only cue that this is the Review gate.
* Nothing else broke in the flows exercised; the deeper task lifecycle (real agents, PRs, merges,
  cloud worlds) could not be exercised on this host and is where the bugs you are fixing elsewhere live.

## 2. Open findings (ranked)

### Workflows and coordinators (`src/workflows`, `src/coordinators`)

1. **HIGH — failed workflow-edit checks do not block the merge.** `merge-only.ts:405-441`: when `workflowEdit && !checks.passed` the layers are skipped but the code still parks on `condition(() => confirmed || cancelled)`; any `confirm` merges a workflow edit whose tests/replay-compat failed, contradicting the comment "Never confirm a workflow-edit whose checks failed" and SPEC §4.4. S7 above removes the agent vector; a human can still do it. Fix (needs a new version pin, since it changes the parked predicate): park on `condition(() => cancelled)` when checks failed.
2. **MED — credential policy fails open.** `software-dev.ts:1738`, `agent-turn-lease.ts:240`: `resolveCredentialOrder(...).catch(() => undefined)` turns a failed policy activity into "any account of this provider" (`account.ts pickFor`), which on a hosted cell can lease another organization's login. Fix (version-gated): treat a failed resolution as denied.
3. **MED — GitHub landing wait can hit Temporal's history cap.** `software-dev.ts:3115-3130, 3395-3400`: `queued`/`waiting` PR states re-run preflight + 2–3 publishes every 30 s with no continue-as-new (≈3–4k events/hour; a PR waiting half a day terminates at 51,200 events). Fix: park on `condition(() => cancelled || providerChangeEpoch > seen)` when webhooks are configured, or poll coarsely and skip unchanged snapshots.
4. **MED — budget coordinator never rotates once a `pending` request's task dies.** `budget.ts:391-394` (no liveness sweep, unlike merge/agent/account).
5. **LOW** — `account.ts:511-514` `Promise.race([condition, sleep])` leaks a timer per iteration (`condition(fn, ms)` is equivalent); `account.ts:534-539` unguarded `inUse--` can double-release; `agent-turn-lease.ts:125,250` restores status to `'active'` instead of the pre-lease status; `merge-only.ts:541-547` / `just-do.ts:265` return `failed` or let a non-infra failure escape without `destroyWorld` (remote sandboxes stay billed); `merge-only.ts:372-380` runs the 45-minute checks after a cancel; `software-dev.ts:3235-3245` swallows a `CancelledFailure` into `{merged:false}`.

10. **MED — E2B transport timeouts escalate instead of retrying** (from the removed root note). `isTransportError()` does not recognise "request handshake timed out" / "operation was aborted due to timeout"; remote Codex state sync runs in `finally` and can replace a successful turn result; E2B creation retries only 3× before escalating. 11. **MED** — `merge.ts:263-275` (duplicated `git-broker.ts:735-745`): `conflictMarkerFiles` passes every landed path as argv to `git grep`; on E2BIG it silently reports "no markers".
12. **MED** — `container.ts:306-321`, `checkpoint.ts:101`: host-side reads follow symlinks inside the bind-mounted world; an agent can `ln -s ~/.ssh/id_ed25519 leak` and have it checkpointed/served. Fix: `realpath` + confinement in `filePath`.

## 4. Trade-offs taken in this change

* **Legacy agent-mail secret still accepted** (installation-wide) so forwarders configured before this change keep delivering; it is no longer shown anywhere. Rotate it away (`kv agent-mail:secret`) once every organization has re-copied its per-organization webhook URL.
* **Agents need `review:approve` to confirm a Review gate or re-route a review.** The built-in maintainer, administrator and god profiles carry it; developer does not. Existing customized profiles are not touched, so an installation that customized its maintainer profile must add the capability by hand (built-in profiles that still match a historical snapshot are upgraded automatically).
* **Package manifests are JSON-only on master already** (upstream decision); this branch adds only the hosted-cell `agentMcp` refusal.
* **Skills moved under `skills/organizations/<orgId>/`.** Skills saved before this change stay in the global directory and remain visible to every organization (they were operator-reviewed by then); new saves are tenant-scoped.
* **Coordinator edit** (`agent-queue.ts` sweep) is a pure state fix that emits the same commands; the boot-time coordinator health probe covers the (unlikely) case of a singleton that had already hit the buggy path.
* **On a hosted cell, already-installed packages that declared `agentMcp` or used a module manifest fail to restore at boot** with a clear per-package error; self-hosted installs are unaffected.
* **Workflow code was not edited.** Items 1–5 need version pins and a replay plan; they are left open deliberately rather than risk wedging in-flight executions.
